# GTNH Journey 1.1.8 live test

This pass verifies global server acceleration through 128x and the read-only Botania Mana Debug Tool while preserving the 1.1.7 non-blocking backup path.

## Setup

- GTNH 2.9.x Java 25 singleplayer/integrated server.
- Replace 1.1.7 with `gtnhjourney-1.1.8.jar`; never keep both JARs.
- Keep automatic Journey backups enabled so speed and backup wall-clock behavior are exercised together.
- Have one ordinary Botania Mana Pool available; a Diluted Mana Pool is useful for the capacity check.

## Speed command surface

Run each command and then `/journey speed status`:

- `/journey speed 1` -> target 20 TPS
- `/journey speed 2` -> target 40 TPS
- `/journey speed 4` -> target 80 TPS
- `/journey speed 8` -> target 160 TPS
- `/journey speed 16` -> target 320 TPS
- `/journey speed 32` -> target 640 TPS
- `/journey speed 64` -> target 1280 TPS
- `/journey speed 128` -> target 2560 TPS

Expected:

- all values are accepted for the session;
- status reports the selected multiplier and target TPS;
- unsupported runtimes fail closed to 1x rather than partially applying a speed;
- restart resets the session to 1x.

The target is a requested simulation rate. 64x and 128x are best-effort and may run below 1280/2560 actual TPS when the CPU cannot execute complete server ticks that quickly.

## Global tick compatibility

At 1x, note progress for several ordinary tick-based systems. Then briefly repeat at 8x, 16x and, if stable, 32x or higher.

Check at minimum:

- a GregTech machine with visible processing progress;
- a vanilla furnace or another vanilla tick-based process;
- a Botania flower/mana-transfer setup or another Botania tile that updates every world tick;
- one additional modded tick-based machine available in the world, for example Forestry, IC2 or EnderIO.

Expected:

- all ordinary server/world-tick systems accelerate together;
- Journey does not directly call GregTech, Botania or other TileEntity update methods;
- high-speed 64x/128x still advances complete `MinecraftServer.tick()` cycles rather than one selected mod subsystem;
- real-time systems that intentionally use wall-clock time are not expected to scale with Journey speed.

## Botania Mana Debug Tool

1. Run `/journey botania debug tool` as the integrated-server owner/operator.
2. Hold the granted `Botania Mana Debug Tool`.
3. Right-click an ordinary Mana Pool.
4. Transfer some mana into or out of the pool and right-click again.
5. If available, right-click a Diluted Mana Pool too.

Expected:

- chat reports exact current mana, total capacity, free mana, fill percentage and coordinates;
- an ordinary pool reports runtime capacity based on current + available space, normally 1,000,000 mana;
- a Diluted Mana Pool reports its smaller runtime capacity, normally 10,000 mana;
- right-clicking an unrelated block reports that it is not a compatible Mana Pool;
- inspection does not add/remove mana or otherwise mutate the pool;
- the debug tool itself does not become Journey research.

## Backup coexistence

Play through at least one automatic Journey backup while speed is above 1x.

Expected:

- backup scheduling remains based on real wall-clock time rather than accelerated ticks;
- no return of the 1.1.6-style 10-20 second server freeze at backup start;
- world saving remains enabled;
- a completed backup still contains the expected world snapshot structure.

## Failure capture

If a speed tier crashes, deadlocks, produces a repeated large `Can't keep up!` spiral, or a normal tick-based mod fails to accelerate, return to 1x if possible and attach:

- `logs/latest.log` covering the speed change;
- `/journey dump` from the same session;
- the exact speed tier that triggered the problem;
- the specific machine/flower/process that did not scale;
- for Botania tool problems, the exact pool type and the chat result shown by the tool.
