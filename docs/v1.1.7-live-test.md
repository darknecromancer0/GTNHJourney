# GTNH Journey 1.1.7 live test

This pass verifies the periodic integrated-server freeze reported on 1.1.6 when automatic Journey backups start.

## Reported 1.1.6 signature

The affected world produced `Can't keep up!` spikes at Journey backup starts, including roughly 19.3 s, 16.0 s and 18.5 s stalls. During those stalls the client could visually break blocks or request GUIs, but the authoritative server did not tick, so blocks reappeared and GUI actions arrived only after recovery.

## Setup

- GTNH 2.9.x Java 25 singleplayer/integrated server.
- Replace 1.1.6 with `gtnhjourney-1.1.7.jar`; never keep both JARs.
- Keep automatic Journey backups enabled with the normal 300 second interval.
- Use the same large world when possible.

## Five-minute cadence regression

1. Enter the world and play continuously through at least three automatic Journey backup starts.
2. Around each expected backup start, break/place ordinary blocks and open several machine GUIs.
3. Keep the client focused on normal gameplay; do not pause the game during the observation window.
4. After each backup completes, inspect `latest.log` around the timestamp encoded in the Journey backup filename.

Expected:

- no 10-20 second integrated-server stop at Journey backup start;
- no ghost block breaks caused by the server failing to tick;
- machine GUIs open normally rather than arriving many seconds late;
- staging and ZIP work continue in the background and a valid Journey backup completes;
- vanilla world saving remains enabled throughout;
- `latest.log` does not show a large `Can't keep up!` spike synchronized exactly to every Journey backup start.

Small isolated lag from normal GTNH load is not itself a failure. The regression is the repeated backup-synchronized multi-second stall.

## Backup integrity smoke test

- let one automatic backup complete;
- verify the ZIP contains the real world directory as its top-level folder;
- verify `level.dat` and `region` are present;
- leave the world normally and confirm the current live world also saves successfully;
- `/journey backup status` should report idle after completion and the completed backup path/duration.

## Failure capture

If a large backup-synchronized stall remains, attach:

- `logs/latest.log` covering at least two backup starts;
- `/journey dump` during or immediately after a backup;
- the exact Journey version shown in the dump;
- approximate freeze duration observed in-game.
