# GTNH Journey 1.1.26 Sorting and Command-History Design

## Scope

Target remains GTNH 2.9.0-beta-2 / NEI 2.8.111-GTNH on Minecraft 1.7.10.

1.1.26 changes two interaction models:

1. command suggestion navigation must no longer steal vanilla chat-history Up/Down;
2. Journey item presentation is split into four independent dimensions: **View × Group × Order × Latest**.

No research identity, retrieval, death recovery, speed, explosions, snapshots, spawner identity or GTNH NEI filtering semantics are intentionally changed by this release.

## Command suggestion navigation

Vanilla Up/Down remains authoritative for chat and command history.

When a suggestion popup is visible:

- `Shift+Down` moves selection one suggestion down;
- `Shift+Up` moves selection one suggestion up;
- `Tab` accepts the selected suggestion;
- plain `Up` and `Down` are never consumed by Journey;
- when no popup is visible, Shift+Up/Down is not consumed either.

The existing global server-command completion source remains authoritative. Journey does not keep a parallel command tree for popup navigation.

## View layer: what is shown

Mutually exclusive content views:

- **ALL**: ordinary native NEI;
- **J / RESEARCHED**: researched Journey states;
- **F / FAVOURITE**: researched exact states contained in favourites;
- **C / CREATIVE**: native NEI universe plus Journey-only exact variants;
- **D / DELETE**: researched Journey states presented for deletion.

The old **N / NEWEST view is removed**. Its activity behavior becomes the independent L modifier described below.

Existing item interactions remain unchanged:

- J/F/C: LMB gives 1 item, RMB gives one natural stack, Shift+RMB fills available main-inventory slots;
- J: Alt+LMB adds an exact state to F;
- F: Alt+RMB removes an exact state from F;
- D retains delete semantics.

## Four-dimensional presentation model

Every Journey-owned view is rendered from canonical source data using:

1. **View**: J/F/C/D;
2. optional **Group** policy;
3. optional **Order** policy;
4. optional **L / Latest activity** modifier.

Group, Order and L are independent. None may destructively rewrite another layer or reuse the already-reordered visible list as input.

### Group dropdown

The first compact dropdown in the header is the **Group** selector.

Available values:

- **None**: no grouping;
- **N / Native NEI family**: group native item/meta families according to `ItemList.items`; Journey-only exact variants remain adjacent to their native family anchor;
- **M / Mod**: group by owning mod;
- **T / Type**: broad semantic category;
- **K / Kind**: narrow inventory-sorter-like family.

Only one Group policy may be active at once. Selecting the active value again or choosing None disables grouping.

### Order dropdown

The second compact dropdown is the **Order** selector.

Available values:

- **None**: no extra order policy; the current Group's canonical order is used, or canonical Journey order if Group=None;
- **U / Unlock**: newest first by initial research time;
- **A / Alphabetical**: localized display name ascending with stable registry/meta/NBT fallback;
- **F+ / Favourite added**: newest favourite addition first, available only in F.

Only one Order policy may be active at once. Selecting the active value again or choosing None disables Order.

### L / Latest activity modifier

L is a separate latch/toggle and can be active with any Group and any Order.

L uses presentation activity:

- first research counts as activity;
- successful Journey issuance counts as activity;
- successful C issuance of an ordinary native NEI item also counts as presentation activity without researching that item or adding it to J.

L never mutates research chronology, favourite chronology, Group metadata or Order metadata.

## Combination semantics

### No Group, no Order, L off

`J` shows the canonical researched Journey list.

### J + L

Pure activity order over the complete J set, newest activity first. This replaces old NEWEST/N behavior.

No Group or previous Order may leak into this mode.

Critical invariant:

`J + N + L` followed by Group=None must immediately become pure `J + L`. Native-family structure from N must disappear completely.

### J + U

No grouping. Individual researched states are ordered only by initial unlock time, newest learned first.

### J + N

Native NEI families are kept together and arranged by canonical native NEI family order. Family members remain in native order.

### J + U + N

This is a supported first-class combination.

- N defines the grouping unit: native NEI family;
- U defines family priority: the family containing the most recently first-learned visible member ranks ahead of older families;
- internal family order remains canonical native NEI order;
- ties use deterministic native-family order.

Example: if Oxygen Cell is newly learned, the whole Fluid Cell family moves according to U; Oxygen Cell is not ripped out of its family.

### J + N + L

- N defines native NEI families;
- L ranks whole families by most recent activity of any visible family member;
- issuing Water Cell moves the whole Fluid Cell family, not only Water Cell;
- internal family order remains canonical native order;
- U/A, if disabled, have no residual effect;
- the current NEI page is retained where valid.

### J + U + N + L

- N defines family boundaries;
- L is the primary dynamic priority by latest activity;
- U is the deterministic secondary priority for groups whose latest-activity comparison is equal/absent;
- internal native family order remains intact.

Equivalent composition rules apply to M/T/K groups:

- Group defines what moves together;
- L may reprioritize whole groups by most recent member activity;
- Order provides the canonical/secondary ordering of those groups or their members;
- disabling L immediately restores pure Group+Order output from canonical data.

## Type and Kind classification

Classification is layered and fail-safe.

Preferred evidence order:

1. concrete Minecraft item classes (`ItemArmor`, `ItemSword`, `ItemFood`, `ItemBow`, `ItemTool`, block items, potions, etc.);
2. tool classes and Forge item capabilities;
3. Ore Dictionary names and common GTNH material-form names;
4. native NEI / Item Subsets metadata where safely available;
5. narrow registry/mod-specific adapters only where generic evidence is insufficient;
6. deterministic `Misc` fallback.

Broad **T / Type** examples:

- Armor
- Weapons
- Tools
- Machines
- Components
- Power / Batteries
- Food / Drink
- Blocks / Building
- Fluids / Containers
- Materials
- Crops / Seeds
- Magic Components
- Storage
- Misc

Narrow **K / Kind** examples:

- Helmet / Chestplate / Leggings / Boots
- Sword / Bow
- Pickaxe / Axe / Shovel
- Hammer / Wrench / Cutter / Scanner
- Battery
- Ingot / Plate / Rod / Wire / Gear / Gem / Ore / Dust / Cell
- other stable families as evidence permits

Classification failure never removes an item from the view.

## GTNH NEI search and Item Subsets parity

This is a release-blocking architectural invariant.

Journey does **not** implement its own independent parser for GTNH search prefixes or Item Subsets.

Membership pipeline:

1. build the canonical content set for J/F/C/D;
2. pass candidate membership through the real GTNH NEI filter stack using native representative semantics;
3. apply Item Subsets and the native SearchField grammar, including `@`, `%`, `#` and all other prefixes/operators supported by the installed GTNH NEI build;
4. only after membership is finalized, apply Journey Group;
5. then Order;
6. then L activity prioritization.

Sorting is forbidden from reintroducing an item rejected by SearchField or Item Subsets.

For Journey-only exact variants, a native NEI representative determines subset/mod/family membership where available, while the exact Journey state remains the displayed and retrievable stack.

Examples:

- `J + @Avaritia + N + U + L`: NEI first restricts membership to Avaritia; Journey then groups/sorts only those surviving states.
- selecting a GTNH Item Subset such as GregTech machines must never allow M/T/K/L to bring Thaumcraft or another excluded mod back into the list.

Search/filter updates may reset/clamp pagination because membership changed. Activity-only reorder must not.

## Favourite-added chronology

Current favourites persist membership but do not reliably persist explicit addition chronology.

1.1.26 adds bounded per-player favourite-added chronology for F+.

Migration rules:

- existing favourites are never removed;
- missing chronology is seeded deterministically from current Journey research/activity history;
- new explicit additions receive normal add chronology;
- adding an already-favourited exact state is an idempotent no-op and does not fabricate a newer add time;
- remove then later re-add creates a new explicit favourite-add event.

## Presentation activity for C

C may display native NEI items that are not researched.

To allow C + L without corrupting research data, 1.1.26 maintains a bounded client/server presentation-activity identity for successful C issuance.

Requirements:

- issuing an unresearched C item updates presentation activity;
- it does not unlock/research that item;
- it does not add that item to J;
- the identity is sufficient to rank its native Group family in C;
- researched exact Journey states continue using their normal activity identity.

## Per-view UI memory

J/F/C/D remember their Group, Order and L choices independently during the client session.

Examples:

- J: `N + U + L`;
- F: `Group=None + F+`;
- C: `N + L`;
- D: `K + A`.

Switching views restores that view's controls.

ALL/native NEI does not own or alter Journey sort state.

## Compact UI layout

The existing NEI **G / expand** control keeps its existing meaning and label.

To avoid button overflow, 1.1.26 does not render every sort option as a permanent 16px button.

Journey adds only three persistent sorting controls immediately to the left of the existing G/expand region:

- `[L]` independent Latest toggle;
- `[N▼]` Group dropdown showing the active Group abbreviation (`-`, N, M, T or K);
- `[U▼]` Order dropdown showing the active Order abbreviation (`-`, U, A or F+ in F).

The exact displayed glyph may be compacted to fit the GTNH font, but Group and Order are distinguished by fixed position and full tooltip text.

Dropdown menus show full labels:

Group:

- None
- N Native NEI family
- M Mod
- T Type
- K Similar kind

Order:

- None
- U Unlock order
- A Alphabetical
- F+ Favourite added (F only)

The old N content-mode button is removed, freeing one Journey-header slot.

If width is still insufficient at narrow panel sizes:

- L and the two dropdown selectors have priority over exposing every menu entry directly;
- dropdown contents render vertically rather than consuming horizontal header width;
- existing page controls, search widgets and G/expand must never overlap Journey controls;
- Journey controls may hide at extreme widths rather than overlap native NEI controls.

## Page-retention invariant

This is release-blocking.

Issuing, favouriting, deleting, learning or otherwise changing activity while on page 2+ must not automatically return to page 1 unless the resulting filtered list genuinely has fewer pages than the current page.

Mandatory example:

1. use J + N + L on page 2+;
2. issue Fluid Cell;
3. all visible Fluid Cell native-family states reorder together according to L;
4. the current page remains the same index, clamped only if the list now has fewer pages;
5. switch Group from N to None while leaving L on;
6. output becomes pure J + L activity order with no residual N family grouping.

Refresh algorithm:

1. capture current zero-based page before publication;
2. rebuild visible membership from canonical View + native GTNH filters;
3. rebuild Group + Order + L from canonical metadata;
4. call the NEI item-panel update;
5. restore the captured page clamped to the new last page;
6. only explicit View/Group/Order/filter changes that intentionally request a reset may select page 1.

Successful issuance/activity must always use the non-reset path.

## Persistence boundaries

- research remains server-authoritative;
- favourites membership remains server-authoritative;
- favourite-added chronology is server-authoritative;
- presentation activity required for C ordering is bounded and must not change research membership;
- Group/Order/L are UI preferences and are session-local per view in 1.1.26 unless later requested otherwise.

## Testing requirements

### Command history

- plain Up/Down with popup visible are not consumed;
- Shift+Up/Down moves popup selection;
- Tab accepts selection;
- no popup leaves all arrow behavior to vanilla.

### GTNH filters

- Item Subsets membership is identical before and after every Group/Order/L combination;
- `@`, `%`, `#` and installed native NEI search operators remain authoritative;
- sorting never reintroduces rejected items;
- Journey exact variants use native representative membership without losing exact retrieval identity.

### Combination matrix

Pure tests cover at minimum:

- J
- J + L
- J + U
- J + N
- J + U + N
- J + N + L
- J + U + N + L
- M/T/K with U/A and with/without L
- F + F+
- C + N + L with both researched and unresearched native items
- D combinations without changing delete semantics

### Mandatory Fluid Cell regression

1. create multiple native families including Fluid Cell;
2. activate J + N + L;
3. set page to 2+;
4. issue Fluid Cell;
5. assert all Fluid Cell family variants move together;
6. assert internal native order remains unchanged;
7. assert page does not reset to 1;
8. switch Group=N to Group=None while leaving L enabled;
9. assert pure activity order and zero residual N grouping.

### Migration and state

- old favourites migrate without loss;
- F+ survives reload;
- re-add semantics are idempotent until explicit remove/re-add;
- J/F/C/D remember Group/Order/L independently;
- old NEWEST view state migrates to J + L where applicable;
- no duplicate or missing research states are introduced by presentation sorting.

4. Run formatter and complete Forge build/test gate on one exact SHA.
5. Verify the runtime JAR itself reports 1.1.26 before artifact upload.
