# GTNH Journey 1.1.26 Sorting and Command-History Design

## Scope

Target remains GTNH 2.9.0-beta-2 / NEI 2.8.111-GTNH on Minecraft 1.7.10.

This release changes two interaction models:

1. command suggestion navigation must no longer steal vanilla chat-history Up/Down;
2. Journey item presentation must separate **what is shown** from **how it is ordered**.

No research identity, retrieval, death recovery, speed, explosions, snapshots, spawner identity or NEI filtering semantics are intentionally changed by this release. Favourite persistence is extended only with chronology metadata required by F+.

## Command suggestion navigation

Vanilla Up/Down remains authoritative for chat-command history.

When a suggestion popup is visible:

- `Shift+Down` moves selection one suggestion down;
- `Shift+Up` moves selection one suggestion up;
- `Tab` accepts the currently selected suggestion;
- plain `Up` and plain `Down` are never consumed by Journey and therefore continue to navigate Minecraft chat history;
- when the popup is absent, Shift+Up/Down is not consumed either.

The existing global server-command completion source remains authoritative. This change only modifies navigation keys.

## View modes

Journey has mutually exclusive content modes:

- **ALL**: ordinary native NEI view;
- **J / RESEARCHED**: researched Journey states;
- **F / FAVOURITE**: researched Journey states contained in favourites;
- **C / CREATIVE**: native NEI universe plus Journey-only exact variants;
- **D / DELETE**: researched Journey states presented for deletion.

`NEWEST` / the old **N view mode is removed**. Newest/activity behavior becomes part of the sorting layer instead of a separate content mode.

Existing click semantics remain unchanged:

- migration note: the old N view is removed; the letter N is reused below for Native NEI order;
- J/F/C: LMB gives 1 item, RMB gives one natural stack, Shift+RMB fills available main-inventory slots;
- J: Alt+LMB adds to favourites;
- F: Alt+RMB removes from favourites;
- D retains delete semantics.

## Two-axis presentation model

Each Journey-owned view has two independent ordering controls:

1. **zero or one primary sort**;
2. optional **L / Latest priority** modifier.

A primary sort is therefore radio-like while active, but clicking the currently active primary-sort button again clears it. This explicitly enables transitions such as `J + N + L` -> `J + L`.

Primary sort and L must never leak state into one another. Turning a primary sort off or switching to another primary sort recalculates from canonical view data, not from the already-reordered visible list.

### Baseline order with no primary sort and no L

To preserve existing J/F/D behavior, a Journey research-backed view with neither a primary sort nor L uses research unlock chronology, newest learned first. C with neither control uses its canonical merged Native NEI + Journey-exact order.

This baseline is an implementation default, not a hidden selected primary sort. No sort button appears active.

### Primary sorts

The initial set is:

- **N / Native NEI order**: follow `ItemList.items`; Journey-only exact variants remain adjacent to their native item/meta family.
- **U / Unlock order**: first research time, newest learned first. In C, researched entries use unlock chronology and unresearched native entries fall back after them in canonical native order.
- **A / Alphabetical**: localized display name ascending; stable fallback by registry id, metadata and canonical NBT.
- **M / Mod groups**: group by owning mod; groups have a stable mod-name/id order and entries within each group retain Native NEI family/order.
- **T / Type groups**: broad functional categories such as Armor, Weapons, Tools, Machines, Components, Power/Batteries, Food/Drink, Blocks/Building, Fluids/Containers, Materials, Crops/Seeds, Magic Components, Storage and Misc.
- **K / Kind-family groups**: narrower inventory-sorter-like families such as helmets, chestplates, leggings, boots, swords, bows, pickaxes, axes, shovels, hammers, wrenches, cutters, scanners, batteries, ingots, plates, rods, wires, gears, gems, ores, dusts, cells and similar families.
- **F+ / Favourite-added order**: time an exact state was added to F, newest addition first. This primary sort is available only in F.

At most one primary sort is active at a time. Zero is valid.

## L / Latest priority modifier

L is a latch/toggle, independent from the primary sort.

L ranks by **Journey presentation activity**. Presentation activity consists only of:

- first successful research/unlock of an exact Journey state;
- successful item issuance from a Journey-owned J/F/C panel.

Favourite add/remove, deletion, search/filter changes and merely viewing an item do not count as L activity.

For researched states, existing Journey activity chronology remains the authoritative starting history. 1.1.26 extends the sorting activity layer so successful issuance of a C-only native item can also participate in L without researching that item or changing Journey research identity.

C-only activity is UI/sorting metadata, not research data. It must never cause a C item to appear in J or F unless normal research later occurs.

### L with no primary sort

`J + L` means pure activity order: the complete J set is shown newest-activity first. It is not limited to a fixed count. This replaces the old N/Newest view behavior.

The same rule applies to F/C/D:

- F + L shows the full favourite set in presentation-activity order;
- C + L shows the full creative/debug union in presentation-activity order, with never-active entries following in canonical C order;
- D + L shows the full deletable researched set in presentation-activity order.

Critical invariant: after using `J + N + L`, clearing N to reach `J + L` must immediately produce pure activity order. Native family ordering from N must have **zero residual effect**.

### L with a primary sort

L reprioritizes **whole primary-sort groups/families**, never individual items out of their group.

Example for `J + N + L`:

1. Fluid Cell and its native subtype/exact family are currently on page 4.
2. The player issues one Fluid Cell.
3. Presentation activity for that exact state updates.
4. The **entire Native NEI family containing Fluid Cell** moves ahead of less-recent families.
5. The family's internal Native NEI ordering remains unchanged.
6. The current page is retained where valid; issuing the item must not force page 1.

Equivalent rules:

- **N + L**: rank Native NEI item/meta families by most recent member activity; preserve internal native order.
- **U + L**: rank unlock-order units/families by recent activity while preserving deterministic unlock-order tie-breaking.
- **A + L**: rank alphabetical item families by recent activity; preserve alphabetical order inside equal-priority/family boundaries.
- **M + L**: rank whole mod groups by most recent activity of any visible member; preserve Native NEI-derived order inside the mod group.
- **T + L**: rank broad type groups by most recent activity of any visible member; preserve category-internal deterministic order.
- **K + L**: rank narrow semantic families by most recent activity of any visible member; preserve family-internal deterministic order.
- **F+ + L**: rank favourite states/families by recent activity, with favourite-added chronology as deterministic secondary order.

L never destructively rewrites the underlying primary sort. Disabling L immediately returns to the primary sort's canonical order. Clearing the primary sort while L remains enabled immediately returns to pure L activity order.

## Per-view sort memory

Sort configuration is remembered independently for J, F, C and D during the client session.

Examples:

- J may remember `N + L`;
- F may remember `F+` without L;
- C may remember `N`;
- D may remember `K + L`.

Switching views restores that view's remembered primary sort and L state.

ALL/native NEI view does not own Journey sort state and must remain untouched.

## UI layout

The old N content-mode button is removed from the Journey header.

A compact sorting strip is placed immediately to the left of the existing `G / expand` control.

Visible controls:

- `L` is rendered as an independent toggle/latch;
- primary-sort buttons are `N`, `U`, `A`, `M`, `T`, `K`, plus `F+` in F;
- zero or one primary-sort button may be active;
- clicking the active primary-sort button clears it while preserving L;
- tooltips state the full sort name and whether L affects groups/families for that sort.

If horizontal space is insufficient:

- L and the currently selected primary sort remain visible;
- lower-priority sort buttons may move behind G/expand;
- existing J/F/C/D/S/T controls must not overlap page navigation or search widgets.

## Canonical ordering inputs

Sorts operate from canonical source data on every refresh, never from the previously published NEI panel list.

Inputs include:

- research unlock chronology;
- Journey presentation activity chronology;
- favourite-added chronology;
- native `ItemList.items` order/family anchors;
- localized display names;
- registry namespace/mod ownership;
- Minecraft item classes, tool classes, Ore Dictionary names and available NEI/subset metadata for type/kind classification.

Unknown or optional-mod items fail into deterministic fallback categories rather than disappearing.

## Presentation activity persistence

Research-backed activity keeps using the existing authoritative Journey activity history.

For C-only native entries, 1.1.26 adds a bounded presentation-activity history keyed by exact stable item identity sufficient for sorting. It is persisted independently from research membership so C issuance can remain recent across reconnect/restart without polluting J.

If a C-only item later becomes normally researched, its existing presentation activity may be reconciled into the research-backed sort activity without creating a duplicate visible state.

The activity history is bounded and fail-closed: unresolved registry identities are skipped rather than converted into fallback items.

## Favourite-added chronology migration

Current favourites persist membership but not explicit add timestamps/order.

1.1.26 adds bounded per-player favourite-added chronology.

For existing favourites without chronology:

- no favourite is removed;
- migration seeds a stable order derived from current Journey research/activity chronology;
- after migration, new additions append/update the favourite-added chronology normally;
- re-adding an already-favourited state is an idempotent no-op and does not fabricate a new add timestamp unless the state was first removed and then explicitly re-added.

## Type and kind classification

Classification is layered and fail-safe.

Preferred evidence order:

1. concrete Minecraft item classes (`ItemArmor`, `ItemSword`, `ItemFood`, `ItemBow`, `ItemTool`, block items, potions, etc.);
2. tool classes and Forge item capabilities where available;
3. Ore Dictionary names and common GTNH material-form prefixes/suffixes;
4. native NEI/subset/category metadata where safely accessible;
5. registry/mod-specific narrow adapters only when generic evidence is insufficient;
6. deterministic `Misc` fallback.

No item is excluded merely because classification fails.

Broad **T** categories and narrow **K** families are separate policies so future category changes do not destabilize the other sort.

## Page-retention invariant

This is a release-blocking regression contract.

Issuing, favouriting, deleting, learning or otherwise changing activity while viewing page 2+ must not automatically return the panel to page 1 unless the resulting filtered/sorted list genuinely has fewer pages than the current page.

Refresh algorithm:

1. capture current zero-based page before publishing a new list;
2. rebuild the visible list from canonical view + filter + sort state;
3. call the NEI item-panel update;
4. restore the captured page clamped to the new last page;
5. only explicit view/filter/sort changes that semantically request a reset may intentionally select page 1.

Activity caused by item issuance must use the non-reset path even when L causes groups to move.

Changing sort controls intentionally may reset to page 1 because the user explicitly changed ordering. Merely issuing an item while L is active may not.

## Search and Item Subsets interaction

Existing native NEI filter parity remains authoritative.

Sorting happens on the set that belongs to the current Journey view, while Search/Item Subsets continue to decide visibility through native representative semantics.

A filter update may reset/clamp pagination as required by changed result count. Item issuance/activity alone may not.

## Persistence boundaries

- Research data remains server-authoritative and unchanged in membership semantics.
- Favourite membership remains server-authoritative.
- Favourite-added chronology is server-authoritative because it must survive reconnect/restart and support F+ consistently.
- Research-backed presentation activity uses the existing authoritative activity data.
- C-only presentation activity is persisted separately and must not alter research membership.
- Primary sort and L state are client UI preferences and do not need world persistence in 1.1.26; session-local per-view memory is sufficient unless later requested.

## Testing requirements

### Command history

- plain Up/Down with popup visible must not be consumed;
- Shift+Up/Down moves popup selection;
- Tab accepts selection;
- absence of popup leaves all arrow behavior to vanilla.

### Ordering

Pure tests cover every primary sort with and without L, plus zero-primary-sort states.

Mandatory scenario:

1. create several Native NEI families including Fluid Cell;
2. set J + N + L;
3. place player on page 2+;
4. issue Fluid Cell;
5. assert all Fluid Cell family variants move together according to activity priority;
6. assert their internal native order remains unchanged;
7. assert page does not reset to 1;
8. click N again while keeping L enabled, producing J + L;
9. assert output is pure activity order and contains no residual N-family ordering;
10. assert the current page is still retained/clamped rather than blindly reset by the issuance refresh.

Additional tests cover:

- baseline J/F/D with no controls preserves newest-unlock-first behavior;
- baseline C with no controls preserves canonical C union order;
- L off restores exact canonical primary sort;
- clearing a primary sort while L stays on produces pure L order;
- M/T/K move complete groups rather than one item;
- C-only item issuance updates presentation activity without adding the item to J;
- F+ uses add chronology and survives reload;
- old favourites migrate without loss;
- J/F/C/D remember sort state independently;
- C still includes native NEI plus Journey exact variants;
- Search and Item Subsets still produce identical membership before/after sorting;
- no duplicate or missing research states are introduced by ordering.

2. Add a 1.1.26 release contract and live regression checklist.

5. Verify built runtime JAR reports 1.1.26 before artifact upload.
