# GTNHJourney 1.1.0 World Safety Design

## Goal

Add three server-side safety features directly to GTNHJourney 1.1.0:

1. Consistent rotating world backups every 5 minutes.
2. An optional global explosion blocker with rate-limited chat diagnostics.
3. A player cleanse command for removable negative status effects, including IC2/GTNH radiation.

The features are intentionally isolated from Journey research identity, retrieval, migration, and NEI behavior.

## Release and compatibility

- Target version: `1.1.0`.
- Base: current `release/v1.0` / GTNHJourney 1.0.4.
- Target pack remains GTNH 2.9.0-beta-2 on Minecraft/Forge 1.7.10.
- No separate companion mod or external backup script is required.
- Existing Journey research data and snapshot data are not repurposed for world backups.

## 1. Rotating world backups

### User-visible behavior

World backups are enabled by default.

While a world is running, GTNHJourney creates an additional backup every 5 minutes of server uptime. The cadence is wall-clock/server-runtime based rather than Minecraft day time, so `/time set`, sleeping, or dimension time changes do not alter the interval.

Commands:

- `/journey backup status`
- `/journey backup now`
- `/journey backup on`
- `/journey backup off`

`on`/`off` persist in the Journey config across restarts. Manual `backup now` is allowed even when automatic backups are disabled.

### Consistency model

Backups use the approved synchronous model:

1. Run only on the authoritative server side.
2. Force-save player data and all loaded dimensions/chunks before copying.
3. Keep the server thread blocked while the world directory is copied into the archive so the files do not change underneath the backup.
4. Write to a temporary archive first.
5. Atomically promote/rename the temporary archive only after the ZIP closes successfully.

A short pause is accepted in exchange for a coherent restore point.

If saving or ZIP creation fails, the failure is logged and reported to an operator/player who manually requested the backup. A failed or partial backup never counts toward rotation and never causes a good previous backup to be deleted.

### Storage and rotation

Backups are stored outside the world directory under a Journey-owned directory such as:

`gtnhjourney-backups/<safe-world-name>/`

Archive names use a sortable timestamp, for example:

`backup-2026-08-28_02-40-00.zip`

Only the three newest successful archives for that world are retained.

Rotation order is safety-first:

1. Create and close the new archive successfully.
2. Promote it from temporary name to final name.
3. Enumerate successful final archives.
4. Delete oldest archives until at most three remain.

Temporary `.tmp` files are ignored by rotation and cleaned on a later successful backup/startup where safe.

The backup root must never be placed inside the source world directory, preventing recursive self-inclusion.

### Scope of archive

The archive contains the complete active world/save directory needed to restore the world, including dimension folders and player/world data stored inside that save. It does not copy the entire Prism instance, mod JARs, config directory, screenshots, or logs.

### Concurrency and lifecycle

- At most one backup may run at a time.
- If an automatic cadence occurs while a manual/automatic backup is already running, the extra automatic request is skipped rather than queued.
- Server shutdown must not start a new automatic backup.
- Backup state is cleared between integrated/dedicated server sessions in the same JVM.

## 2. Global explosion control

### Default and commands

Explosion blocking is **disabled by default**. Normal GTNH explosions therefore continue to work immediately after installing 1.1.0.

Commands:

- `/journey explosions status`
- `/journey explosions off` — disable explosions globally.
- `/journey explosions on` — restore normal explosions globally.

The naming controls the explosions themselves, not the guard: `off` means explosions are prevented. The state persists in the Journey config across restarts.

Changing the setting requires integrated-server owner/operator permission. Reading `status` may be allowed to ordinary players.

### Cancellation semantics

When explosions are off, GTNHJourney subscribes to Forge `ExplosionEvent.Start` and cancels every cancelable explosion before detonation.

This is intentionally global and includes, where they travel through Forge's explosion event:

- GregTech machine/boiler explosions,
- TNT,
- creepers,
- vanilla/modded entity explosions,
- bed-style explosions,
- other mod explosions.

GTNHJourney does not attempt to selectively preserve entity damage or block damage for a canceled explosion. The whole explosion event is canceled.

If a mod bypasses Forge's explosion pipeline entirely, Journey cannot guarantee interception; such cases must be logged/live-tested rather than guessed around with invasive coremods.

### Diagnostic chat message

For a canceled explosion, Journey tries to identify a useful source at/near the explosion origin in this order:

1. Source/exploder entity display name/type when meaningful.
2. Tile entity or block at the explosion origin, including a GregTech machine name when safely resolvable.
3. Registry/display name of the block at the origin.
4. Generic `Explosion` fallback.

Example:

`GTNH Journey: Explosion from Large Bronze Boiler cancelled at 123, 64, -45.`

Source-name resolution is best-effort and must never allow a broken optional-mod object to prevent cancellation.

### Notification throttle

Chat notification is globally rate-limited to at most one message every 5 seconds to avoid TNT chains or repeated machine faults spamming chat.

Suppressed cancellations are counted. The next emitted notification may append the accumulated count, e.g. `(+14 more cancelled)`.

Cancellation itself is never rate-limited: every explosion is still canceled while the setting is off.

Notifications go to online players with sufficient operator/owner permission rather than broadcasting safety diagnostics indiscriminately to every multiplayer user.

## 3. Player status cleanse

### Command

Add:

`/journey cleanse`

This acts on the issuing player only and removes currently active removable negative potion/status effects.

It includes vanilla and modded effects that are exposed through Minecraft's active `PotionEffect` collection and are classified as harmful/negative by their `Potion` definition.

GTNH radiation is explicitly in scope. Current GTNH sources apply radiation using `IC2Potion.radiation` as a normal `PotionEffect`, so `cleanse` must remove that effect as well.

Examples in scope include radiation, poison, wither, weakness, slowness, mining fatigue, nausea/confusion, blindness, hunger, and compatible modded negative potion effects.

### Explicit non-goals

`cleanse` does not rewrite persistent progression or world systems that are not active potion/status effects, including:

- Thaumcraft permanent Warp/progression,
- world pollution values,
- quest/progression data,
- player research,
- arbitrary mod capability/NBT state,
- equipment or inventory items that immediately reapply a debuff.

If a radioactive item remains in inventory, radiation may be re-applied on the next mod tick. The command still correctly clears the current effect; it does not provide temporary immunity.

Positive potion effects are preserved.

The command reports how many negative effects were removed. It is player-only and does not require operator permission because it affects only the caller.

## 4. Configuration

Add a dedicated safety/backup section to Journey's existing Forge config with at least:

- `worldBackupsEnabled=true`
- `worldBackupIntervalSeconds=300`
- `worldBackupRetention=3`
- `explosionsEnabled=true`

For 1.1.0 the UI commands expose only on/off/status/manual backup, not arbitrary cadence or retention editing. Interval and retention are configurable for recovery/testing but defaults remain exactly 300 seconds and 3 backups.

Configuration values are bounded to safe ranges in code; malformed values cannot produce a tight per-tick backup loop or unbounded retention.

The existing research compatibility configuration remains unchanged.

## 5. Component boundaries

New functionality should be split into focused server-side units rather than added wholesale to `CommandJourney` or `GTNHJourney`:

- Backup scheduler/state: decides when a backup is due and prevents overlap.
- Backup writer/rotator: saves, archives, promotes, and rotates files.
- Explosion policy/state: stores and reports whether explosions are enabled.
- Explosion event handler: cancels and records diagnostics.
- Explosion source resolver: best-effort naming only, isolated from cancellation correctness.
- Notification throttle: deterministic 5-second aggregation logic.
- Player cleanse service: determines/removes negative active effects.
- Command glue: parses `/journey backup`, `/journey explosions`, and `/journey cleanse` and delegates to the services.

`GTNHJourney` remains composition/registration glue.

## 6. Failure handling

World safety must fail closed with respect to data corruption and fail safe with respect to gameplay availability:

- Never delete an existing successful backup because a new backup failed.
- Never publish a half-written ZIP under a final backup filename.
- Never run two archive writers concurrently.
- A backup IOException must not crash the server.
- A source-name lookup exception must not allow an explosion through when explosions are off.
- If config loading fails to supply the new keys, defaults apply: backups enabled, explosions enabled.
- `cleanse` ignores invalid/missing potion registry entries rather than crashing.

## 7. Testing strategy

Implementation follows TDD.

Backup tests must cover:

- exact 300-second default cadence,
- enabled/disabled/manual semantics,
- no overlap,
- successful three-file rotation,
- failed-new-backup preserves all prior good archives,
- temporary files are not treated as good backups,
- source world directory is never recursively included,
- deterministic archive path/name handling.

Explosion tests must cover:

- default explosions enabled,
- `off` cancels every Forge Start event presented to the handler,
- `on` does not cancel,
- permission policy for mutations,
- five-second notification throttle and suppressed-count aggregation,
- resolver failures do not change cancellation result.

Cleanse tests must cover:

- negative effects removed,
- positive effects preserved,
- radiation effect removed,
- empty/no-effect player is a no-op,
- malformed/unregistered potion ID cannot crash cleanup.

Existing full Journey test suite, Forge build, checkstyle/Spotless, runtime version guard, and artifact upload remain mandatory before merging to `release/v1.0`.

## 8. Live validation checklist

Before calling 1.1.0 complete, live-test in GTNH 2.9.0-beta-2:

1. Start a real world and verify automatic backup after about 5 minutes.
2. Trigger four manual backups and verify only the newest three successful ZIPs remain.
3. Restore one ZIP into a copied instance/world slot and verify it loads.
4. Run `/journey explosions off`, ignite TNT, and verify no explosion damage plus one diagnostic message.
5. Trigger a GregTech machine/boiler explosion path where practical and verify cancellation/source naming.
6. Verify repeated explosions within five seconds remain canceled without chat spam.
7. Run `/journey explosions on` and verify ordinary explosion behavior returns.
8. Apply radiation and another negative effect, run `/journey cleanse`, and verify both disappear while a positive effect remains.

## 9. Out of scope for 1.1.0

- Automatic restore/rollback command for entire worlds while the server is running.
- Cloud/off-device backup upload.
- Differential/incremental ZIPs.
- More than three retention tiers or daily/weekly retention policies.
- Selective explosion allow/deny lists.
- Temporary explosion immunity per player/chunk.
- Purging persistent non-potion systems such as Warp or pollution.
