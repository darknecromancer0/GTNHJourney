# GTNH Journey 1.1.1 backup live-test

Target: GTNH `2.9.0-beta-2`, NEI `2.8.111-GTNH`.

Use the production `gtnhjourney-1.1.1.jar` from the final exact-SHA green CI artifact. Keep an independent copy of the test world from before this pass.

## 1. Version and initial status

1. Replace the previous Journey jar with `gtnhjourney-1.1.1.jar`.
2. Load the test world fully.
3. Run `/journey backup status` before the first automatic backup.

Expected:

- GTNH reports Journey `1.1.1`;
- status reports automatic backups enabled by default, `300s`, `keep 3`, and `idle`;
- before any completed backup in the session, last duration is `n/a` and the last-result text says no backup has completed this session;
- the five-minute automatic cadence begins after the world has actually loaded.

## 2. Large-world automatic backup without the old compression freeze

Use a world large enough that 1.1.0 synchronous ZIP compression was visibly slow.

1. Continue normal gameplay until the first automatic backup becomes due.
2. While it is running, move, open inventories and interact with ordinary machines.
3. Run `/journey backup status` during and after the operation if practical.

Expected:

- there may be a short save/flush hitch while player/world data are forced to disk;
- the long ZIP-compression phase no longer blocks the server tick loop;
- status can report `running` while the worker is active, then returns to `idle`;
- after completion, status reports a non-`n/a` duration and a successful last result;
- no second backup overlaps the active worker.

## 3. ZIP structure and restore shape

Open the newest archive under `gtnhjourney-backups/<world-name>/`.

Expected:

- the ZIP has the real save-directory name as its top-level folder;
- `level.dat`, `region/`, dimension folders and other save contents are inside that folder;
- there is no loose root-level `level.dat` or root-level `region/` entry;
- the archive can be extracted as one world directory suitable for placing back under `saves/`.

## 4. Rotation and temporary files

Allow or manually start at least four successful backups.

Expected:

- only the newest three successful `.zip` archives remain;
- a completed backup leaves no `.zip.tmp` for that operation;
- rotation occurs only after the new final ZIP exists;
- an unrelated stale temporary file is not counted as a successful backup.

## 5. Manual backup while automatic backups are disabled

1. Run `/journey backup off`.
2. Confirm `/journey backup status` reports disabled.
3. Run `/journey backup now`.
4. Wait for status to return from `running` to `idle`.

Expected:

- automatic cadence is disabled and persists through config save;
- manual backup still starts in the background;
- a successful manual backup creates a normal final ZIP and updates last duration/result.

Re-enable automatic backups afterwards if desired with `/journey backup on`.

## 6. Shutdown during an active backup

Use a large world so the worker remains active long enough to observe.

1. Start `/journey backup now`.
2. Confirm status reports `running`.
3. Save and quit while the backup is still active.
4. Reopen the instance and load the world again.

Expected:

- Journey stops accepting new backup work as shutdown begins;
- shutdown may wait for the already-running ZIP worker to finish;
- the temporary world save-suppression state is restored before shutdown continues to its final save;
- the instance closes without leaving the world permanently unable to save;
- the world reopens normally and recent state survives.

## 7. Final evidence

Attach these if any backup regression remains:

- `latest.log` covering world load, backup start/completion and shutdown if tested;
- `/journey backup status` text before and after the backup;
- the exact archive filename and approximate size;
- a ZIP directory listing showing the top-level world folder;
- `/journey dump` if any unrelated Journey research/panel regression appears during the same run.
