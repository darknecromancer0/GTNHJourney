# GTNH Journey 1.1.4 live-test checklist

Target runtime: GTNH `2.9.0-beta-2`, NEI `2.8.111-GTNH`, Java 25 launcher with Java 8-compatible mod bytecode.

Use a disposable copy of a real world. Keep a known-good backup outside the active instance before starting this pass.

## 1. Persistence and research integrity

- Research several ordinary items, exit to title, reopen the same world and confirm persistence.
- Restart the full Minecraft instance and confirm the same researched set returns again.
- Research a Botania Daybloom in more than one ordinary runtime state and confirm Journey does not create meaningless duplicates.
- Repeat with a wand/tool state that previously produced transient-NBT duplicates and confirm the semantic state remains stable.
- Retrieve the tested states and confirm the recreated items still have the intended meaningful data.

## 2. Journey panel and Shift+right-click retrieval

- Open Journey/Researched in NEI and confirm the authoritative researched set appears.
- Shift+right-click a normal stackable item and confirm retrieval fills the expected natural stack without corrupting inventory state.
- Shift+right-click a non-stackable item and confirm only its valid non-stackable amount is produced.
- Repeat after moving items between inventory slots and after reopening NEI.
- Confirm J/N ordering and active native NEI filters still behave normally after retrieval.

## 3. Command hints

- Open chat and type `/journey ` slowly. Confirm command hints appear without a client exception.
- Type `/journey speed ` and confirm live suggestions include `1`, `2`, `4`, `8`, and `status`.
- Confirm ordinary vanilla Tab completion still works for the same command surface.
- Reopen chat several times and confirm command hints continue working after GUI recreation.

## 4. Diagnostic dump

Run `/journey dump`, open the generated file under `logs/`, and confirm it contains the new integrity fields:

- client mirror stack count;
- server authoritative research count;
- server syncable count and server-only oversized count;
- Journey mode;
- NEI search text and Journey-applied filter provider information;
- authoritative, semantic and visible panel stack counts;
- command-hint registration, resolver path/failures and last suggestion count;
- backup running state, last result and last duration;
- research-key display names, or a safe UNAVAILABLE marker when a name cannot be resolved.

The dump must be observational only. Running `/journey dump` must not add, delete, unlock, restore or reorder research states.

## 5. Manual backup

- Run `/journey backup status` and note the current state.
- Run `/journey backup now` to start a manual backup.
- Keep playing while it runs and confirm the server remains responsive.
- Wait for the manual backup completion notification.
- Confirm the ZIP appears under `gtnhjourney-backups/<world-name>/` and contains the real world directory as its top-level folder.
- Open the archive and verify `level.dat` plus representative region/player data are present.

## 6. Automatic backup and wall-clock cadence

- Ensure automatic backups are enabled.
- Record real wall-clock time and the current newest backup timestamp.
- Change Journey speed during the interval and keep the world active.
- Confirm the next automatic backup follows the configured wall-clock interval rather than accelerated game ticks.
- Confirm the automatic backup completion notification is delivered.
- Confirm rotation keeps the configured number of newest successful backups.

## 7. Session speed command and permissions

- Run `/journey speed status` as a normal player. Confirm status is readable without mutation permission.
- As the integrated-server owner or operator, run `/journey speed 2`, then `4`, then `8`.
- At each setting confirm `/journey speed status` reports the requested multiplier and target TPS.
- Try an invalid value such as `/journey speed 3`; it must not change the current valid state.
- If the transformed server pacing hook is unavailable, Journey must report unsupported and remain safely at 1x rather than pretending acceleration succeeded.

## 8. 2x / 4x / 8x gameplay regression matrix

At 2x, 4x and 8x separately, observe representative systems long enough to prove they advance through normal server ticks:

- GregTech machine processing and energy usage;
- Botania generation, transfer and flower behavior;
- vanilla furnace progress and output;
- fluid movement through a representative fluid network or tank setup;
- redstone clocks, repeaters or another timing-sensitive redstone circuit;
- player movement, inventory interaction and ordinary network synchronization.

The speed feature must not directly tick TileEntity instances or special-case individual machines. All tested systems should advance because the normal MinecraftServer tick cadence is faster.

## 9. Backup behavior while accelerated

- Start a manual backup at 2x, 4x and 8x at least once across the pass.
- Confirm backup preparation/completion remains correct and no save suppression remains stuck after completion.
- Confirm the automatic backup interval is still wall-clock based while the game runs at 8x.
- Inspect `/journey backup status` after completion and verify last result plus duration are retained.

## 10. Restart reset to 1x

- Leave the world running at 8x.
- Save and exit normally.
- Restart the server/world.
- Run `/journey speed status` before changing anything.
- Confirm session speed has reset to 1x / 20 TPS after restart.
- Confirm research persistence and backup configuration persistence are unaffected by the speed reset.

## 11. Final smoke pass

- Verify `/journey help` lists the speed command.
- Verify `/journey backup`, `/journey explosions`, `/journey cleanse`, recovery commands and the Debug Researcher Tool still work as expected.
- Run one final `/journey dump` and retain it with the live-test notes.
- Check `latest.log` for Journey, Mixin, networking, backup or server-tick exceptions.
- Record the exact GTNH Journey JAR filename and confirm it is `gtnhjourney-1.1.4.jar`.
